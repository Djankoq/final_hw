# Каркас краулера контактных данных

## Volatile, AtomicInteger и singleton-кэш

В пакете `ru.example.crawler.task` добавлены:

- `StopFlag`: одноразовый `volatile boolean`, методы `requestStop()` и `isStopped()`.
  Рабочие потоки проверяют флаг в цикле и выходят после установки `true`.
  Флаг обеспечивает видимость записи между потоками, но не прерывает блокирующие операции.
- `AtomicCounter`: `increment()` и `get()` на основе `AtomicInteger`.
  Инкремент атомарен; обычный `volatile int` не делает операцию `++` атомарной.
  Диапазон ограничен типом `int`: переполнение не предотвращается.
- `SingletonCache`: единственный экземпляр через `getInstance()`, ленивое значение через `get()`.
  `AtomicReference<String>` публикует строку посредством `compareAndSet(null, candidate)`.
  При гонке могут создаваться несколько кандидатов, но сохраняется и возвращается всем
  только победивший объект. Создание кандидата не имеет побочных эффектов.
  Значение неизменяемо; сброса кэша нет. Singleton существует в пределах загрузчика классов.

```shell
mvn test
java -cp target/classes ru.example.crawler.task.AtomicPerformanceDemo
```

В IDE можно запустить `main` класса `AtomicPerformanceDemo`.
Сначала четыре потока одновременно читают кэш и увеличивают счётчик до установки
флага остановки главным потоком. Главный поток ждёт начала работы каждого участника,
даёт нагрузке поработать ещё 200 мс, устанавливает флаг и получает результаты через `Future`.
Сумма локальных чисел операций сверяется с общим счётчиком, ссылки на объект кэша
сравниваются через `==`. Ожидания ограничены тайм-аутами, пул освобождается в `finally`.
JUnit проверяет конкурентную нагрузку, остановку активных потоков и остановку до старта.

Затем сравниваются `volatile + AtomicInteger + AtomicReference` и аналогичные операции
на `synchronized` с 1, 4 и 8 потоками. Каждый поток выполняет 200 000 итераций:
чтение флага, получение значения кэша, инкремент. После двух прогревов идут пять
замеров с чередованием порядка вариантов; выводится медиана и число итераций в секунду.
Создание потоков исключено из времени; запуск через общий барьер, завершение и сбор
результатов включены. Измеряется преимущественно работа уже заполненного кэша.

Пример локального запуска (Java 21.0.1, 20 доступных JVM процессоров):

| Потоки | Итоговый счётчик | volatile/Atomic, мс | synchronized, мс |
|---|---:|---:|---:|
| 1 | 200 000 | 1,066 | 8,593 |
| 4 | 800 000 | 12,172 | 91,689 |
| 8 | 1 600 000 | 25,497 | 200,958 |

При остановке проверены 22 011 607 инкрементов; установка флага, завершение всех потоков
и сбор результатов заняли 0,309 мс. Это не измерение чистой задержки чтения `volatile`.
В этой нагрузке atomic-вариант быстрее мониторного. При увеличении числа потоков
его общая пропускная способность падает: все участники конкурируют за один счётчик.
Чтение заполненного кэша требует только `AtomicReference.get()`, CAS нужен при инициализации.
`volatile` обеспечивает видимость флага, atomic-операции защищают отдельные обновления;
вся итерация из нескольких операций не является одной атомарной транзакцией.
После запроса остановки поток может закончить уже начатую итерацию.

Это учебный замер общей нагрузки в одной JVM, а не изолированной стоимости каждого
примитива. Результаты зависят от JIT, оборудования, планировщика и фоновой нагрузки;
они не означают, что atomic-переменные быстрее при любом алгоритме. Для строгого
сравнения нужны отдельные микробенчмарки JMH с несколькими запусками JVM.

## Ограниченный потокобезопасный буфер

`BoundedBuffer<T>` в пакете `ru.example.crawler.task` — FIFO-буфер фиксированной
вместимости. Конструктор принимает положительный размер; `null` запрещён.
`put(T)` ждёт свободного места, `take()` ждёт появления элемента.
Оба метода объявляют `throws InterruptedException`.

Один `ReentrantLock` защищает очередь, два `Condition` (`notFull`, `notEmpty`)
разделяют ожидания producer и consumer. Захват выполняется через `lock()`,
освобождение — через `unlock()` в `finally`. `await()` освобождает блокировку
на время ожидания; после пробуждения условие снова проверяется в `while`.
Прерывание ожидания передаётся вызывающему коду; сам захват через `lock()`
не является прерываемым.

По умолчанию операция вызывает `signal()` для противоположной стороны.
`new BoundedBuffer<Integer>(64, true)` включает `signalAll()`: просыпаются все
ожидающие соответствующего условия, но каждый повторно проверяет доступность
ресурса под блокировкой.

```shell
mvn test
java -cp target/classes ru.example.crawler.task.BufferPerformanceDemo
```

Демонстрация запускается отдельно через `main`: четыре producer передают
100 000 уникальных чисел четырём consumer через буфер на 64 элемента.
Каждый поток выполняет заранее определённое число операций; ошибки передаются
через `Future`, ожидание ограничено тайм-аутом, исполнитель освобождается
в `finally`.

Сравниваются `ReentrantLock + signal`, `ReentrantLock + signalAll` и
`synchronized + wait/notifyAll` с одинаковой очередью и нагрузкой.
У монитора обе роли используют один набор ожидания, поэтому нужен `notifyAll()`.
После трёх прогревов выполняются семь измерений с чередованием порядка вариантов.
Выводятся медиана времени и число переданных элементов в секунду (на элемент
приходятся `put` и `take`). Создание потоков исключено из замера; завершение задач
и получение результатов входят в него. Проверяется контрольная сумма.
JUnit отдельно проверяет FIFO, аргументы, блокировку обеих сторон, прерывание
и отсутствие потерь/дубликатов в обоих режимах уведомления.

Пример локального запуска: `signal` — 24,19 мс, `signalAll` — 21,50 мс,
`synchronized` — 29,90 мс. Это учебный замер в одной JVM: результат зависит
от JVM, оборудования, вместимости и числа потоков и не доказывает универсальное
превосходство одного способа синхронизации.

## Банковские переводы и синхронизация

`BankDataCollector` хранит счета, журнал `Item` и `processedCount`. Суммы задаются
целым числом копеек (`long`). Все операции чтения и записи защищены `synchronized`
на одном экземпляре банка. Поэтому списание, зачисление, запись ключа и увеличение
счётчика выполняются атомарно; захвата нескольких мониторов и циклического ожидания нет.
Это простая схема с ограничением: независимые переводы тоже выполняются последовательно.

- `openAccount(id, balance)`, `deposit(id, amount)` — создание и пополнение счёта.
- `collectItem(item)` — перевод без ожидания; `false` означает дубликат или недостаток средств.
- `collectItem(item, timeoutMillis)` — ожидание средств до указанного тайм-аута.
- `isAlreadyProcessed(key)` — информационная проверка; защита от дубликатов выполняется
  внутри `collectItem`, в одной критической секции с изменением балансов.
- `incrementProcessed()` — внутренний синхронизированный метод: счётчик увеличивается
  только после успешного перевода, поэтому внешний код не может испортить статистику.
- `getBalances()` и `getItems()` возвращают неизменяемые снимки.

Ожидание использует `TimeUnit.NANOSECONDS.timedWait(this, remaining)`, вызывающий
`wait(millis, nanos)`. Монитор освобождается на время ожидания. Условие проверяется
в цикле, включая повторную проверку ключа после пробуждения. Пополнение и успешный
перевод вызывают `notifyAll()`. Тайм-аут возвращает `false`, прерывание передаётся
вызывающему коду как `InterruptedException`. Отрицательные суммы, неизвестные счета,
переводы на тот же счёт и повторное использование ключа с другими данными отклоняются.
Переполнение проверяется до изменения балансов.

`BankPerformanceDemo` запускается из `ContactCrawlerApplication` или отдельно:

```shell
mvn test
java -cp target/classes ru.example.crawler.task.BankPerformanceDemo
```

В IDE можно запустить `main` класса `BankPerformanceDemo`.
Нагрузочная проверка выполняет 40 000 переводов в 8 потоках с одновременным чтением
снимков и повторной отправкой каждого перевода. Проверяются общая сумма, конечные
балансы и счётчик. Четыре JUnit-теста дополнительно проверяют конкурирующие дубликаты,
встречные переводы, пробуждение всех ожидающих потоков, тайм-аут, прерывание,
некорректные операции и переполнение.

Для сравнения производительности используется отдельный минимальный баланс:
обе версии выполняют одинаковые 400 000 переводов, но одна защищена `synchronized`,
а другая намеренно содержит гонки данных. После 3 прогревов выполняются 7 раундов
с чередованием порядка. Создание потоков исключено из замера; запуск через общий
сигнал и ожидание завершения включены. Выводятся время, итоговые балансы и счётчик.
Пример локального запуска: медианы 5,330 мс и 0,104 мс соответственно; в одном из
несинхронизированных раундов счётчик оказался 392 785 вместо 400 000.
Гонки могут не проявиться в отдельном запуске. Время ошибочной версии не является
ускорением корректного решения; JIT может существенно преобразовать её цикл.
Это учебное сравнение, а не строгий микробенчмарк JMH.

## Цель

Создать Spring Boot-приложение, которое в дальнейшем сможет обходить сайты организаций и извлекать открытые телефоны, email, адреса и ссылки. В текущей работе реализован каркас приложения и продемонстрирована работа с потоками.

## Архитектура

- `ContactCrawlerApplication` — точка входа и запуск демонстрационных задач.
- `ContactCrawlerService` — сервисный слой будущего краулера. В дальнейшем здесь можно организовать загрузку страниц, извлечение ссылок и контактов.
- `CounterWorker` — отдельная задача, созданная наследованием от `Thread`.
- `LoggerTask` — задача, реализующая интерфейс `Runnable` и передаваемая объекту `Thread`.
- `ThreadStatesDemo` — демонстрация всех шести состояний на трёх потоках `DemoWorker-1`, `DemoWorker-2`, `DemoWorker-3`.

Предполагаемый дальнейший поток данных: стартовый URL → загрузчик HTML → извлечение ссылок → очередь непосещённых страниц → извлечение контактов → удаление дубликатов → сохранение результата.

## Этапы выполнения

1. Создан Maven-проект на Spring Boot 3 с Java 17.
2. Добавлен сервис `ContactCrawlerService` как основа бизнес-логики краулера.
3. Добавлен поток `CounterWorker`, созданный через наследование от `Thread`.
4. Добавлена задача `LoggerTask`, запущенная через `Runnable` в потоке `LoggerThread`.
5. Каждый поток пять раз выводит своё понятное имя и порядковый номер итерации.
6. Через `Thread.getAllStackTraces()` выводятся все активные потоки JVM, включая созданные потоки.
7. Метод `join()` обеспечивает корректное ожидание завершения обеих задач.

## Запуск

```shell
mvn spring-boot:run
```

Или запустить метод `main` класса `ContactCrawlerApplication`.

Только демонстрацию состояний можно запустить через `main` класса
`ThreadStatesDemo` в IDE или из корня проекта без Maven (нужен JDK 17+):

```shell
java --source 17 src/main/java/ru/example/crawler/task/ThreadStatesDemo.java
```

## Демонстрация состояний потоков

При запуске приложения сначала создаются три демонстрационных потока.
Каждый проходит последовательность
`NEW → RUNNABLE → WAITING → BLOCKED → TIMED_WAITING → TERMINATED`.
Главный поток наблюдает реальные значения `Thread.getState()` и выводит
имя и состояние каждого потока на каждом этапе:

```text
DemoWorker-1 -> NEW
DemoWorker-2 -> NEW
DemoWorker-3 -> NEW
DemoWorker-1 -> RUNNABLE
DemoWorker-2 -> RUNNABLE
DemoWorker-3 -> RUNNABLE
```

Далее аналогично выводятся остальные четыре состояния для всех трёх потоков.

| Состояние | Причина |
| --- | --- |
| `NEW` | Объект создан, `start()` ещё не вызван. |
| `RUNNABLE` | Поток выполняет активный цикл до изменения атомарного флага. |
| `WAITING` | `CountDownLatch.await()` без таймаута ожидает сигнал главного потока. |
| `BLOCKED` | Поток пытается войти в `synchronized`, пока монитор занят главным потоком. |
| `TIMED_WAITING` | Второй `CountDownLatch.await(30, TimeUnit.SECONDS)` ожидает сигнал с таймаутом. |
| `TERMINATED` | Метод `run()` завершился; главный поток дождался этого через `join()`. |

Главный поток разрешает следующий этап только после наблюдения текущего
состояния у всех трёх потоков. Это позволяет увидеть нужные состояния,
не полагаясь на случайный порядок выполнения. Ожидание состояния ограничено
10 секундами: при сбое программа сообщает ожидаемое и фактическое состояние
и освобождает рабочие потоки. Таймаут 30 секунд не задерживает обычный запуск:
главный поток снимает ожидание сразу после наблюдения `TIMED_WAITING`.
Короткие промежуточные переходы между этапами не протоколируются.

## Сравнение stream() и parallelStream()

Класс `StreamPerformanceDemo` создаёт `ArrayList<Integer>` из 1 000 000
псевдослучайных чисел в диапазоне `[0, 1 000 000)` с seed `42`.
Оба варианта обрабатывают один список: оставляют чётные числа,
умножают их на `2L` и вычисляют сумму типа `long`.

```shell
java --source 17 src/main/java/ru/example/crawler/task/StreamPerformanceDemo.java
```

Демонстрация также вызывается при запуске основного приложения.
После 10 прогревочных выполнений каждого варианта программа делает 15 замеров
с чередованием порядка запуска. `System.nanoTime()` измеряет весь конвейер
`filter → mapToLong → sum`; генерация списка, проверка и вывод исключены.
Печатаются все замеры, минимум, медиана, среднее, максимум и ускорение по медиане.
Каждая сумма проверяется независимым циклом: ожидается `500644900156`,
количество чётных чисел — `500052`.

Это учебное сравнение: время зависит от JIT, нагрузки системы, процессора,
памяти и доступности общего пула потоков. Для строгих микробенчмарков нужен JMH
с несколькими запусками JVM. Промежуточные операции Stream ленивые, поэтому
отдельные времена фильтрации и преобразования здесь не измеряются.
